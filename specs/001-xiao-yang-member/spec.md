# Feature Specification: 小扬同学 - AI会员管理助手

**Feature Branch**: `001-xiao-yang-member`

**Created**: 2026-05-14

**Status**: Draft

**Input**: User description: "「小扬同学」是澳门直播协会会员部门的AI负责人（一把手），名称取＂发扬光大＂之意，旨在通过人工智能技术提升会员管理效率，优化入会流程，为会员提供更便捷的服务体验。定位为会员部门的AI管理员，负责统筹会员入会流程、咨询服务及日常管理工作，配合行政同事处理报名表等具体事务，实现会员管理的智能化与数字化升级。"

## Clarifications
- Q: 会员等级划分规则 — 共有几个等级？活跃度和贡献度如何衡量？晋升是否需要审批？ → A: 三个等级：普通会员、高级会员、理事。活跃度按活动参与次数和缴费及时性衡量；贡献度按行业影响力和推荐新会员数衡量。等级晋升由系统根据章程规则自动评估，提交理监事会确认后生效。

### Session 2026-05-14

- Q: 数据规模与增长预期 — 当前会员数？未来增长预期？日常并发咨询量？ → A: 当前约 500 名会员，预期 1-2 年内增长至 3000 名。日常咨询量约 200 次/天。
- Q: 缴费确认机制 — 在线支付不在本期范围，如何确认缴费完成？ → A: 申请人上传缴费凭证截图，「小扬同学」自动存档，由 root 审核确认后将申请状态标记为"已缴费"。
- Q: 角色权限边界 — 各角色（会员/行政同事/理监事会）的数据访问权限如何划分？ → A: 会员仅能查看和修改自己的资料；行政同事可查看所有会员资料，支持批量导出；root 理事拥有终審审批、缴费审核权限，其他理事拥有会员查看权限。

### Session 2026-05-15

- Q: 理监事会终審的预期响应时效？ → A: 初審通过后，理监事会应在 24 小时内完成终審。超过 24 小时未处理时，系统自动向理监事会发送催办提醒。


- Q: 终審不通过后申请人能否重新申请？ → A: 可以重新申请，理监事会驳回时须附具体理由，申请人修正后可再次提交。

- Q: 初審不通过后申请人能否重新申请？ → A: 同样可修正后重新申请。初審不通过时系统告知具体不通过原因（如不符合章程某条），申请人修正后重新提交，重新进入初審流程。

- Q: 申请人收到缴费指引后须在多久内完成缴费？ → A: 7 天内。逾期未缴费视为放弃本次申请，申请状态标记为"已过期"，申请人需重新提交入会申请。

- Q: root 确认缴费凭证的时效要求？ → A: 3 个工作日内。申请人上传缴费凭证后，root 应在 3 个工作日内审核确认，超时系统自动催办。

- Q: 审核结果及缴费凭证等通知通过什么渠道发送？ → A: C 端（申请人/会员）通过小程序订阅消息推送，同时沉淀到小程序内通知收件箱；B 端（root 理事/行政同事）通过 Web H5 站内通知中心查看。涵盖：初審结果、终審结果、root 终審待办提醒、缴费凭证待确认提醒（通知 root）、入会成功通知。

- Q: 咨询服务的使用范围？未登录用户能否使用？ → A: 分两级。未登录用户可咨询通用FAQ（入会条件、费用标准等）；登录后可进行个性化咨询（权益查询、活动信息、历史记录等）。

- Q: AI 知识库检索不到匹配内容时如何处理？ → A: 一律转接人工。当 RAG 相似度低于阈值（0.7）时，系统直接转接行政同事处理，告知用户预计 24 小时内响应。不做模糊猜测回复。

- Q: 转接人工后行政同事的响应时效？ → A: 24 小时内。超时系统自动催办，超过 48 小时未响应升级通知 root。

- Q: AI 回答可能不准确，如何收集用户反馈？ → A: 每条 AI 回复下方提供反馈按钮。差评自动在 Web H5 站内通知中心通知行政同事复核该条回复，并记录用于知识库优化。

- Q: 用户发送违规/敏感内容时系统如何处理？ → A: AI 自行判断内容合规性，不合规时委婉拒绝回复并提示文明交流，同时记录日志供审计。

- Q: 会员状态（在籍/过期/停用）的自动更新条件？ → A: 会费到期自动标记为"过期"，续费缴费确认后自动恢复"在籍"。停用状态由行政同事手动设置（如违规、主动退出等）。

- Q: 会员修改个人信息时，敏感字段（姓名、手机号等）是否需要审批？ → A: 所有字段会员均可自由修改（用户名和身份证号码除外），无需审批。

- Q: 会员尝试越权访问/修改他人资料时如何处理？ → A: 返回友好提示"您无权访问此资源"，后端记录越权日志供审计。

- Q: 行政同事批量导出会员数据的安全措施？ → A: 导出 CSV 格式，记录导出操作日志（操作人、时间、导出条数），导出的 CSV 不含密码等核心敏感字段。

- Q: 活动是否设名额限制？满额后如何处理？ → A: 活动设名额上限，满额后显示"已满"，无法继续报名。

- Q: 会员报名后能否取消？截止时间？ → A: 可取消报名，截止时间为活动开始前 24 小时，超时不可取消。

- Q: 通知发送失败（微信未送达）如何处理？ → A: C 端所有通知同时沉淀到小程序内通知收件箱，用户可在通知中心随时查看；B 端通知仅在 Web H5 站内通知中心展示。

- Q: 活动临时变更或取消时，如何通知已报名会员？ → A: 由行政同事通过通知发送页群发通知。

- Q: 会员等级如何变更？ → A: 等级由行政同事在后台手动修改，不设自动评估机制。普通会员可申请升级，行政同事审核后手动修改等级+年费。

- Q: 等级是否支持降级？ → A: 支持。行政同事在后台手动将会员等级从高级降回普通，年费同步调整。理事固定不变。

- Q: 数据分析报告的生成频率和内容？ → A: 每月 1 号自动生成上月会员分析月报，推送至行政同事。报告包含：会员总数、等级分布、活跃度趋势、入会/流失率、会费缴纳率。
- 系统每月 1 号自动生成会员分析月报并推送行政同事



### Session 2026-05-16

- Q: 会员等级机制如何设计？ → A: 三个等级（普通/高级/理事）。理事为固定几人不变，系统初始化一位 name='root' 的理事。普通年费500，高级年费2000。升级由会员重新申请，行政同事在后台手动修改等级。

- Q: 终審由谁审批？ → A: 所有入会申请的终審统一由 root（理事）一人审批，不再由理监事会多人参与。
- Q: 高级会员有什么特殊权益？ → A: 高级会员享受活动8折优惠（普通会员原价），其他权益暂不区分。理事可后台手动增加，默认初始化一个 name='root' 的理事。

- Q: 会员是否有不可修改的唯一标识？ → A: 有。用户名和身份证号码为唯一不可变标识，入会时填写后终身不可修改。用户名全系统唯一，身份证号码全系统唯一。

- Q: 活动由谁创建和管理？如何通知会员？ → A: 行政同事在 Web H5 活动管理页创建/编辑/取消活动。活动发布后，行政同事通过通知发送页筛选会员群发活动通知。活动取消或变更时，系统自动通知已报名会员。

- Q: 终審表决规则 — 理监事会如何做出终審决定？需要全员投票还是单人审批？ → A: 终審由 root（理事）一人审批（通过或驳回）。
- Q: 初審章程规则由谁管理维护？ → A: 行政同事。行政同事通过后台管理界面维护章程规则（增删改、版本管理），无需理监事会或技术人员介入。
- Q: 缴费凭证审核标准 — root 如何判断凭证有效？ → A: 看截图即可。只要申请人上传了银行转账截图/支付凭证图片，root 查看后即可确认通过，无需逐项核对金额、账号等信息。
- Q: 理监事会成员规模与通知机制？ → A: 终審待办通知仅在 root 的 Web H5 站内通知中心展示。
- Q: 初審 AI 评估方式 — DeepSeek 如何对比申请人资质与章程规则？ → A: 混合模式。硬性条件（年龄、必填字段等）通过结构化规则逐条匹配；软性条件（从业经历质量、资质含金量等）由 LLM 自由评估，综合判断后输出通过/驳回+理由。

- Q: 入会申请缴费环节 — 终審通过后如何触发缴费通知？ → A: 终審通过后系统自动将申请状态从"终審通过"切换为"待缴费"，设置缴费截止日期（7天），通过小程序订阅消息向申请人推送缴费指引通知（含缴费金额、银行账号、截止日期、上传凭证方式），同时可在申请进度追踪页查看。无需人工介入。
- Q: 入会申请状态细化 — 申请人上传缴费凭证后是否需要单独的"待审核缴费"状态？ → A: 需要。申请人上传凭证后状态变为"待审核缴费"，待 root 审核确认后变为"已缴费"。两阶段分离便于追踪缴费审核进度。
- Q: 理监事会和行政同事的操作界面如何安排？ → A: root（理事）通过 Web H5 终審审批页操作（待审列表→查看详情→通过/驳回+理由）。root 通过 Web H5 后台操作：缴费审核页（查看凭证截图→确认/退回）、终審审批页。
行政同事通过 Web H5 后台操作：会员管理后台（搜索/编辑/导出CSV）、通知发送页（筛选会员→群发通知）、章程规则管理页。
- Q: 申请人端需要哪些页面？ → A: 除聊天页和入会申请表外，还需要申请进度追踪页（状态条+缴费指引+倒计时+凭证上传/重传入口）和驳回重申请页（保留原表单数据+显示驳回理由+修改后重新提交）。入会后需会员个人中心（资料/等级+年费/活动报名/通知收件箱）。
- Q: 前端技术方案？ → A: 微信小程序使用原生框架（WXML+WXSS+JS），Web H5 后台页面使用纯 HTML+原生 JS（不引入 Vue/React 等框架）。小程序覆盖申请人/会员端全部页面，Web H5 覆盖申请人备用入口及理监事会/行政同事全部后台页面。
## User Scenarios & Testing *(mandatory)*

### User Story 1 - 新会员入会申请 (Priority: P1)

一位对直播行业感兴趣的个人希望加入澳门直播协会。他通过微信小程序或协会官网访问「小扬同学」，咨询入会条件、流程及费用。在得到清晰解答后，他根据「小扬同学」的指引填写入会申请表。提交后，「小扬同学」根据会员章程对其基本信息、从业经历、相关资质进行初步审核，符合条件则推送给 root（理事）进行终審，不符合则告知原因。审核通过后，「小扬同学」提供缴费指引，申请人完成缴费后收到入会确认通知并正式成为会员。

**Why this priority**: 这是会员部门最核心的业务流程，直接影响协会会员增长和运营效率。

**Independent Test**: 模拟一位新申请人完成从咨询到确认的完整入会流程，验证每个阶段的结果是否符合预期。

**Acceptance Scenarios**:

1. **Given** 用户访问「小扬同学」, **When** 用户询问入会条件, **Then** 系统返回准确的入会条件说明（基本要求、所需材料、费用标准）
2. **Given** 用户决定申请入会, **When** 用户根据指引填写入会申请表, **Then** 系统接收并保存申请表，确认提交成功
3. **Given** 申请表已提交, **When** 「小扬同学」执行初審, **Then** 系统以混合模式（硬性条件结构化匹配 + 软性条件 LLM 评估）对申请人进行初審，输出初審结果（通过/不通过及原因）
4. **Given** 初審通过, **When** root（理事）在 24 小时内完成终審, **Then** 「小扬同学」向申请人发送缴费指引
5. **Given** 申请人收到缴费指引（须在 7 天内完成缴费）, **When** 申请人上传缴费凭证截图, **Then** 系统存档凭证并通知 root 审核；root 查看缴费截图后在 3 个工作日内审核确认，系统发送入会成功通知，会员资料录入数据库

### User Story 2 - 会员咨询服务 (Priority: P1)

用户（无需登录）和会员（已登录）通过「小扬同学」咨询会员权益、福利、常见问题等。系统提供标准化的自动回复，涵盖入会条件、会员权益、活动信息、费用标准等常见问题。当遇到复杂问题或特殊情况时，系统将问题转接至行政同事处理。

**Why this priority**: 咨询服务是会员触达的第一触点，高效的自动回复可大幅减少行政同事的工作量。

**Independent Test**: 模拟会员咨询各种常见问题（权益查询、费用咨询、活动查询等），验证回复的准确性和转接机制。

**Acceptance Scenarios**:

1. **Given** 用户向「小扬同学」提问, **When** 问题属于标准化问题库范围, **Then** 系统返回准确的标准回复
2. **Given** 会员查询自身权益, **When** 会员已登录后发起权益查询, **Then** 系统返回该会员当前可享受的权益清单
3. **Given** 用户提出复杂或特殊情况, **When** 系统识别问题超出自动处理范围或知识库无匹配（置信度<0.7）, **Then** 系统将问题转接至行政同事，并告知用户预计 24 小时内响应
4. **Given** 用户收到 AI 回复, **When** 用户对回复不满意点击差评反馈, **Then** 系统记录反馈并自动通知行政同事复核该回复

### User Story 3 - 会员资料管理与查询 (Priority: P2)

会员通过「小扬同学」查询和更新自己的个人资料（仅限本人）。「小扬同学」自动整理和归档会员资料，维护会员数据库，并更新会员状态（如在籍、停用、过期等）。行政同事可查看所有会员资料并批量导出。root 理事拥有终審审批、缴费审核权限。

**Why this priority**: 会员资料是协会运营的基础数据，自动化管理可确保数据准确性和时效性。

**Independent Test**: 会员查询个人资料 → 验证数据准确性；会员更新部分资料 → 验证更新生效；行政同事查询会员列表 → 验证数据完整性。

**Acceptance Scenarios**:

1. **Given** 会员已登录, **When** 会员发起个人资料查询, **Then** 系统返回该会员的完整个人资料
2. **Given** 会员资料发生变化, **When** 会员在个人中心更新资料, **Then** 系统自动归档更新，旧版本保留备查
3. **Given** 会员状态需要更新, **When** 行政同事或会费到期时系统自动标记为过期、续费后自动恢复, **Then** 会员状态正确更新并记录变更日志

---

### User Story 4 - 会员活动与通知 (Priority: P2)

行政同事通过 Web H5 后台创建和管理活动（名称/时间/地点/费用/人数上限）。活动发布后，行政同事群发通知给目标会员。会员在小程序/Web H5 浏览活动列表、查看详情、报名参加或取消报名。活动报名名额满后自动关闭。活动取消时系统自动通知已报名会员。

**Why this priority**: 活动和通知是维持会员活跃度的关键手段，自动化可确保通知的及时性和覆盖面。

**Independent Test**: 行政同事创建活动 → 群发通知 → 会员报名 → 名额满自动关闭 → 会员取消报名。

**Acceptance Scenarios**:

1. **Given** 协会安排了活动, **When** 行政同事通过系统发布活动通知, **Then** 相关会员收到活动通知
2. **Given** 会员收到活动通知, **When** 会员选择报名参加, **Then** 系统记录报名信息并返回报名确认
3. **Given** 会员会费即将到期, **When** 系统检测到到期时间临近, **Then** 「小扬同学」自动发送续费提醒

---

### User Story 5 - 会员等级与数据分析 (Priority: P3)

系统支持三级会员等级（普通会员/高级会员/理事）。理事可后台手动增加，系统初始化一位 name='root' 的理事。普通会员年费500，高级会员年费2000（享受活动8折优惠）。会员可申请升级等级，由行政同事在后台手动审核修改。

**Why this priority**: 等级管理和数据分析是增值功能，为协会决策提供数据支撑。

**Independent Test**: 行政同事在后台修改会员等级 → 会员端查看等级变更 → 验证年费到期日正确。

**Acceptance Scenarios**:

1. **Given** 系统初始化, **When** 首次部署, **Then** 系统自动创建一位 name='root' 的理事账号
2. **Given** 会员申请升级, **When** 行政同事在会员管理后台手动将等级从普通改为高级, **Then** 会员个人中心显示等级已更新为高级，年费金额变为2000，活动享受8折
3. **Given** 会员查询等级, **When** 会员在个人中心查看, **Then** 系统显示当前等级及对应年费金额

### Edge Cases

- 申请人提交的申请表信息不完整或有明显错误时，系统如何处理？应提示补充或修正，不允许提交不完整申请
- 同一申请人重复提交入会申请时，系统应识别重复并提示已有申请在处理中
- 用户名或身份证号码已被占用时，系统应提示申请人更换
- 终審不通过时，须附具体驳回理由；申请人修正后可重新提交，无需等待冷静期
- 初審不通过时，系统须告知具体不通过原因；申请人修正后可重新提交，重新进入初審流程
- 申请人收到缴费指引后 7 天内未完成缴费，系统自动将申请标记为"已过期"，申请人需重新提交申请
- 申请人上传缴费凭证后，root 3 个工作日内未确认，系统自动催办；超 7 个工作日仍未处理则升级通知行政同事
- 会员忘记账号密码时，需提供找回或重置机制
- 未登录用户仅能访问通用FAQ，无法查询个人权益或历史对话
- AI 知识库无匹配时直接转接人工，不做模糊回答，避免误导用户
- 用户对 AI 回复点差评后，系统自动通知行政同事复核，并标记该知识点待优化
- AI 检测到违规/敏感内容时拒绝回复，提示用户文明交流，违规记录存档供审计
- 转接人工后行政同事 24 小时内未响应，系统自动催办；超 48 小时升级通知 root
- 大量会员同时咨询时，系统需能处理并发请求，不丢失消息
- 协会章程变更导致入会条件变化时，系统需支持章程规则的可配置更新
- 会员个人信息涉及《个人资料保护法》，所有数据传输和存储必须加密
- 会员账号被盗用或密码泄露时，系统需提供账号保护机制（如异常登录检测、密码重置）

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 提供入会咨询服务，包括入会条件、流程、费用的标准化问答
- **FR-002**: 系统 MUST 提供会员权益查询功能，根据会员身份返回对应权益
- **FR-003**: 系统 MUST 支持常见问题的标准化自动回复
- **FR-004**: 系统 MUST 提供入会申请引导功能，指导申请人完成申请表填写
- **FR-005**: 系统 MUST 自动整理和归档会员资料，维护会员数据库
- **FR-006**: 系统 MUST 依据会员章程对申请人进行初審：硬性条件（年龄、必填字段等）结构化规则逐条匹配，软性条件（从业经历质量、资质含金量等）由 DeepSeek LLM 自主评估，综合输出通过/驳回+理由
- **FR-007**: 系统 MUST 根据会员章程（由行政同事维护）为终審提供辅助建议（资格评估摘要），终審由 root（理事）一人审批完成
- **FR-008**: 系统 MUST 支持会员状态维护（在籍、停用、过期等）
- **FR-009**: 系统 MUST 自动发送会员活动通知
- **FR-010**: 系统 MUST 自动发送缴费提醒
- **FR-010a**: 系统 MUST 支持申请人上传缴费凭证截图，自动存档并通知 root 审核确认；root 查看截图即可确认（无需逐项核对金额/账号）
- **FR-010b**: 系统 MUST 通过小程序订阅消息向申请人推送审核结果（初審、终審）及入会成功通知，同时通知沉淀至小程序通知收件箱；通过 Web H5 站内通知中心向 root/行政同事推送待办提醒
- **FR-011**: 系统 MUST 提供活动浏览、报名、取消报名功能，高级会员享受活动8折优惠
- **FR-011a**: 系统 MUST 支持行政同事创建/编辑/取消活动（名称、时间、地点、费用、人数上限）
- **FR-011b**: 系统 MUST 在活动报名名额满后自动关闭报名
- **FR-011c**: 系统 MUST 在活动取消或变更时自动通知所有已报名会员
- **FR-012**: 系统 MUST 支持三级会员等级（普通/高级/理事），其中理事为固定人员，普通与高级按年费区分（普通500/高级2000）。等级变更由行政同事在后台手动操作
- **FR-013**: 系统 MUST 支持会员等级查询，显示当前等级及对应年费金额
- **FR-014**: 系统 MUST 支持复杂问题转接至行政同事处理
- **FR-015**: 系统 MUST 支持通过微信小程序访问
- **FR-016**: 系统 MUST 支持通过协会官网访问
- **FR-017**: 系统 MUST 遵守《个人资料保护法》，确保会员数据安全
- **FR-018**: 系统 MUST 自动发送系统更新通知，在重要功能更新时告知会员
- **FR-019**: 系统 MUST 实施基于角色的访问控制：会员仅能访问自身资料，行政同事可查看所有会员资料并批量导出，root 理事拥有终審审批、缴费审核权限

### Key Entities

- **会员 (Member)**: 包含基本信息（姓名、联系方式、地址等）、用户名（唯一不可变）、身份证号码（唯一不可变）、从业经历、相关资质、会员等级（普通/高级/理事）、年费金额（普通500/高级2000/理事0）、会员状态、入会日期、会费到期日
- **入会申请 (Application)**: 包含申请人信息（含用户名、身份证号码）、申请状态（待审核/初審通过/初審不通过/终審通过/终審不通过/待缴费/待审核缴费/已缴费/已入会/已过期）、提交时间、审核记录（含驳回理由）、缴费截止日期、缴费凭证（截图存档）
- **会员章程 (Constitution Rules)**: 包含入会条件规则、初審筛选标准、资格评估标准（不含等级划分，等级为人工管理）
- **活动 (Event)**: 包含活动名称、时间、地点、费用（普通价/高级折扣价）、人数上限、报名状态、已报名会员
- **通知 (Notification)**: 包含通知类型（活动/缴费/系统更新）、发送时间、接收会员、发送状态

### Non-Functional Requirements

- **数据安全**: 会员资料严格遵守《个人资料保护法》的规定予以保密，传输和存储必须加密；会员应妥善保管个人账号信息
- **可配置性**: 会员章程规则（入会条件、初審筛选标准等）支持可配置更新
- **可用性**: 系统需支持高峰时段的并发咨询请求，不丢失用户消息
- **可维护性**: 重要决策（如入会终審）仍由 root 理事人工把控，「小扬同学」处理标准化操作和初審

- **SC-007a**: 转接人工的咨询问题在 24 小时内得到行政同事首次响应

## Application State Machine *(added 2026-05-16)*

### 入会申请完整流程

```
提交申请 -> 待审核 -> 初審通过 -> 终審通过 -> 待缴费 -> 待审核缴费 -> 已缴费 -> 已入会
              |         |           |          |          |
              重复     初審不通过   终審不通过  7天过期    行政退回
             409       |           |           |          |
                       v           v           v          v
                    驳回重申请   驳回重申请   已过期     重新上传
                    (回待审核)   (回待审核)  (重新申请)  (回待审核缴费)
```

### 各节点详解

| 节点 | 状态 | 触发者 | 页面变化 | 通知目标 |
|------|------|--------|---------|---------|
| 1. 提交 | 待审核 | 申请人 | 跳转: 申请进度追踪页(T025e) ●○○○○ | 无 |
| 2a. AI初審通过（混合模式：硬性结构化+软性LLM） | 初審通过 | AI自动 | 进度页: ●●○○○ 显示"初審通过 ✅" | 订阅消息: 通知申请人"已通过待终審"; 站内通知: 通知 root "新申请待终審" |
| 2b. AI初審不通过（混合模式：硬性结构化+软性LLM） | 初審不通过 | AI自动 | 进度页: 显示驳回理由 + [修改并重新提交]按钮 → 驳回重申请页(T025f) | 订阅消息: 通知申请人驳回理由 |
| 3a. 终審通过 | 待缴费（系统自动） | root理事 | 进度页: ●●●○○ 显示缴费指引(金额/账号/截止日) + 倒计时 + [上传凭证]按钮 | 订阅消息: 通知申请人缴费指引 |
| 3b. 终審不通过 | 终審不通过 | root理事 | 进度页: 显示驳回理由 + [重新申请] → 驳回重申请页(T025f) | 订阅消息: 通知申请人驳回理由(SC-002b: 100%附带) |
| 3c. 终審超时 | 初審通过(不变) | 系统自动 | 无页面变化 | 站内通知: 催办 root(每24h) |
| 4a. 上传凭证 | 待审核缴费 | 申请人 | 进度页: ●●●●◑ 显示"凭证已上传✅ 等待审核" | 站内通知: 通知 root "新凭证待审核" |
| 4b. 缴费超期 | 已过期 | 系统自动 | 进度页: 清空倒计时,显示"申请已过期"+[重新申请] | 订阅消息: 通知申请人申请已过期 |
| 5a. root确认（看截图即可，无需核对金额/账号） | 已缴费→已入会 | root理事 | 跳转: 会员个人中心(T054c) 欢迎页 | 订阅消息: "恭喜成为协会会员🎉" |
| 5b. root退回 | 退回待审核缴费 | root理事 | 进度页: 显示退回原因 + [重新上传凭证] | 订阅消息: 通知申请人退回原因 |
| 5c. root超时 | 待审核缴费(不变) | 系统自动 | 无页面变化 | 站内通知: 3天催办 root; 7天升级通知行政同事 |

## Out of Scope

- 在线支付功能（「小扬同学」提供缴费指引和缴费凭证上传存档，不处理实际支付交易，不对接第三方支付回调）
- 终審由 root 理事人工审核（「小扬同学」仅协助初審，不替代人工终審）
- 协会微信小程序和官网本身的开发（「小扬同学」作为功能模块嵌入现有渠道）
- 视频/语音通话功能（本期仅支持文本交互）
- 多语言支持（本期仅支持中文/粤语，其他语言后续考虑）
